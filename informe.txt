I. INTRODUCCIÓN
--------------------------------------------------------------------------------
El sector financiero requiere mecanismos objetivos para priorizar revisiones y
mitigar pérdidas por incumplimiento. Este proyecto desarrolla un flujo de
ciencia de datos para clasificar clientes según riesgo crediticio elevado
(variable objetivo binaria RiesgoAlto), desde la comprensión de los datos hasta
la comparación de modelos y la exportación de un clasificador reusable.

El enfoque combina análisis exploratorio, preparación reproducible de datos,
entrenamiento de varios algoritmos de aprendizaje supervisado y evaluación con
métricas estándar de clasificación. Los resultados esperados son: (1) un dataset
procesado listo para modelado, (2) una comparación cuantitativa de algoritmos,
(3) un modelo final serializado y un script de verificación de carga, y (4)
criterios claros de éxito alineados con el negocio (detección de alto riesgo con
métricas equilibradas).


II. PROBLEMA, OBJETIVOS Y KPIs
--------------------------------------------------------------------------------

2.1 Descripción del problema
La institución necesita identificar de forma temprana perfiles con alta
probabilidad de presentar riesgo crediticio elevado. La incorrecta calificación
impacta en provisiones, cartera vencida y experiencia del cliente. El problema
se formula como clasificación binaria a partir de atributos demográficos,
laborales, de endeudamiento y de comportamiento en centrales de riesgo.

2.2 Objetivo general
Construir y evaluar modelos de Machine Learning que estimen la etiqueta
RiesgoAlto a partir de datos históricos, seleccionando y exportando el modelo
con mejor desempeño según criterios definidos en el notebook de trabajo.

2.3 Objetivos específicos
- Cargar, limpiar y documentar el dataset crediticio.
- Realizar EDA con estadísticas descriptivas y visualizaciones.
- Codificar variables categóricas, escalar numéricas y evitar fuga de
  información entre entrenamiento y prueba.
- Entrenar y comparar cinco familias de clasificadores en el conjunto de prueba.
- Interpretar resultados (matriz de confusión, reporte de clasificación,
  importancia de variables o coeficientes según el modelo).
- Exportar el modelo final (.pkl) y el dataset procesado (.csv), con rutas
  relativas y verificación mediante script Python.

2.4 KPIs e indicadores de éxito
- F1-Score (clase positiva u macro según el reporte generado): métrica principal
  para elegir el modelo final en la comparativa del notebook (balance entre
  precisión y exhaustividad).
- Accuracy: indicador complementario de acierto global.
- Precision y Recall por clase: lectura del trade-off, especialmente para la
  clase de alto riesgo.
- Matriz de confusión: desglose de errores tipo I/II en términos de negocio.


III. ANTECEDENTES Y FUENTES
--------------------------------------------------------------------------------
El modelado de riesgo crediticio es un campo clásico de aprendizaje supervisado
en finanzas: combinación de variables comportamentales y socioeconómicas para
predecir mora o deterioro (Hand, 2006). La guía CRISP-DM estructura proyectos
de minería de datos en fases entendibles por negocio y TI (Chapman et al., 2000).
Para implementación se utilizó el ecosistema Python y scikit-learn (Pedregosa
et al., 2011), siguiendo buenas prácticas de partición de datos y pipelines
descritas en textos de aprendizaje estadístico (James et al., 2023).


IV. REQUISITOS DEL PROYECTO
--------------------------------------------------------------------------------

4.1 Requisitos funcionales
- Ingestar el archivo CSV crudo del dataset crediticio chileno.
- Predecir RiesgoAlto (0/1) para un registro con el mismo esquema de features
  que el dataset procesado (tras las mismas transformaciones).
- Permitir reentrenamiento y comparación de modelos desde el notebook.
- Exportar artefactos: dataset_crediticio_procesado.csv y modelo_final.pkl.

4.2 Requisitos no funcionales
- Rendimiento: predicción en batch sobre miles de filas debe ser razonable con
  sklearn en CPU; no se exige tiempo real estricto en esta versión.
- Escalabilidad: el diseño por archivos y script facilita mover el .pkl a un
  servicio (API) en una iteración posterior.
- Interpretabilidad: el notebook documenta matrices de confusión, reporte de
  clasificación e importancia de variables o coeficientes según algoritmo.
- Reproducibilidad: semillas fijas (random_state=42) en modelos comparados;
  rutas relativas con os para ejecutar en distintos sistemas operativos.
- Calidad de datos: tratamiento explícito de nulos y eliminación de columnas
  sin valor predictivo (p. ej. índice de fila).


V. DATASET
--------------------------------------------------------------------------------

5.1 Descripción del dataset
Origen de trabajo: tabla de clientes con variables numéricas y categóricas. La
variable objetivo es RiesgoAlto (binaria). Tras preprocesamiento, el archivo
data/processed/dataset_crediticio_procesado.csv contiene solo columnas
numéricas: indicadores binarios y continuos escalados, más la etiqueta. Entre
las dimensiones derivadas figuran, por ejemplo: Tiene_Vehiculo, Edad,
Num_Entidades_Deuda, Tiene_Tarjeta, saldos y ratios, calificaciones y reportes
en centrales, ingreso, ScoreRiesgo, dummies de Sexo, Tipo_Empleo y Ciudad_Chile
(esquema con drop_first en get_dummies), y RiesgoAlto.

5.2 Fuente de los datos
Archivo local del proyecto: data/raw/dataset_crediticio_chile-1-1.csv
(sintético o académico con estructura típica de scoring para el contexto Chile).

5.3 Justificación del dataset
Incluye señales financieras y de buró coherentes con el problema de riesgo;
permite ejercitar todo el pipeline (nulos, categóricas, desbalance, modelado).
El tamaño es adecuado para EDA y para comparar varios algoritmos en un entorno
de laboratorio.


VI. METODOLOGÍA
--------------------------------------------------------------------------------

6.1 Enfoque metodológico
CRISP-DM adaptado a un curso/proyecto: comprensión del negocio y datos, preparación,
modelado, evaluación y despliegue ligero (exportación del modelo) (Chapman et al., 2000).

6.2 Fases del proyecto
1) Comprensión y preparación: carga CSV, limpieza, imputación.
2) EDA: estadísticas y gráficos (distribuciones, relación con RiesgoAlto).
3) Modelado: codificación one-hot, partición train/test, escalado, entrenamiento.
4) Evaluación: métricas en test, matriz de confusión, interpretación.
5) Despliegue académico: guardado de modelo y script de prueba.

6.3 Planificación
Iteraciones centradas en el notebook notebooks/proyecto semana 3 predictivo.ipynb
como artefacto principal; el README documenta revisión en GitHub y ejecución local.
La validación de integración se apoya en src/probar_modelo.py.


VII. ANÁLISIS EXPLORATORIO DE DATOS (EDA) Y VISUALIZACIÓN
--------------------------------------------------------------------------------

7.1 Análisis descriptivo
Se utilizó describe() y conteos para variables clave. El notebook documenta
proporciones de RiesgoAlto y el desbalance entre clases (mayoría de bajo riesgo),
lo cual condiciona la elección de F1 como métrica de comparación.

7.2 Visualizaciones
Incluye entre otras: barras de conteo de RiesgoAlto; gráficos de Peor_Calificacion
y reportes en centrales frente al riesgo; boxplots de Ratio_Saldo_Ingreso y
Num_Entidades_Deuda; KDE de Edad y Variacion_Endeudamiento por clase. Objetivo:
patrones de separación y validación de hipótesis de negocio.

7.3 Hallazgos e interpretación
- El historial de calificaciones y la intensidad de reportes en centrales se
  asocian fuertemente con RiesgoAlto (comportamiento de pago pasado como señal).
- El desbalance hace que el accuracy solo no baste para medir utilidad.
- La edad y la variación de endeudamiento muestran diferencias de distribución
  entre clases, útiles para el modelado supervisado.


VIII. PREPROCESAMIENTO Y CALIDAD DE DATOS
--------------------------------------------------------------------------------

8.1 Limpieza de datos
- Eliminación de la columna No. (identificador de fila sin valor predictivo).
- Imputaciones y reglas documentadas en código para consistencia.

8.2 Tratamiento de valores nulos
- Peor_Calificacion_36M y Peor_Calificacion_12M: fillna(-1) interpretado como
  ausencia de historial.
- Tipo_Empleo nulo: categoría explícita DESCONOCIDO.
- Numéricas restantes: mediana por columna.
- Categóricas de texto restantes: moda.

8.3 Transformaciones
- pd.get_dummies sobre Sexo, Tipo_Empleo y Ciudad_Chile con drop_first=True
  para reducir multicolinealidad.
- Partición estratificada 80/20 (train_test_split con stratify=y).
- StandardScaler ajustado solo con datos de entrenamiento; transformación
  aplicada a train y test; mismo criterio para construir el CSV procesado completo
  alineado con y (según celdas del notebook).

8.4 Evaluación de calidad
Dataset final numérico sin columnas de texto pendientes; dimensiones verificadas
antes de la comparación de modelos; ausencia de escalado “global” previo al split
para evitar fuga de información.


IX. COMPARACIÓN DE TÉCNICAS
--------------------------------------------------------------------------------

9.1 Modelos evaluados
- Regresión Logística (max_iter=1000, random_state=42)
- Árbol de Decisión (max_depth=5, random_state=42)
- Random Forest (n_estimators=100, max_depth=5, random_state=42)
- Gradient Boosting (n_estimators=100, max_depth=3, random_state=42)
- Support Vector Machine — SVC (random_state=42, configuración por defecto del
  clasificador en sklearn)

9.2 Resultados comparativos (conjunto de prueba — salida documentada en notebook)
Regresión Logística    Accuracy ≈ 0.9836  |  F1 ≈ 0.9668
Árbol de Decisión      Accuracy = 1.0000  |  F1 = 1.0000
Random Forest          Accuracy ≈ 0.9988  |  F1 ≈ 0.9977
Gradient Boosting      Accuracy = 1.0000  |  F1 = 1.0000
Support Vector Machine Accuracy ≈ 0.9696  |  F1 ≈ 0.9375

9.3 Justificación de selección
Se seleccionó el modelo con mayor F1-Score en test. En la corrida registrada en
el notebook, el criterio eligió Árbol de Decisión (empate en F1 con Gradient
Boosting; desempate operacional por orden de evaluación o máximo en la
estructura de resultados del código). El modelo exportado en models/modelo_final.pkl
corresponde a esa selección automática.


X. ARQUITECTURA DEL MODELO
--------------------------------------------------------------------------------

10.1 Modelo seleccionado
DecisionTreeClassifier (Árbol de Decisión), según la lógica de mayor F1 en test
del notebook.

10.2 Parámetros e hiperparámetros
- random_state=42 (reproducibilidad)
- max_depth=5 (regularización de complejidad del árbol)
Los demás hiperparámetros quedan en valores por defecto de sklearn para este
estimador.

10.3 Justificación técnica
Los árboles capturan no linealidades e interacciones entre variables sin
requerir ingeniería manual explícita de interacciones; con profundidad limitada
se busca un compromiso sesgo-varianza. La elección final en el proyecto sigue
el KPI acordado (F1 en hold-out).


XI. VALIDACIÓN EXPERIMENTAL
--------------------------------------------------------------------------------

11.1 División de datos
Partición 80% entrenamiento / 20% prueba con estratificación sobre y para
preservar la proporción de RiesgoAlto en ambos conjuntos.

11.2 Validación cruzada
En la versión actual del código la comparación de modelos se reporta sobre una
única partición hold-out. Como extensión metodológica recomendada, se puede
incorporar validación cruzada estratificada (p. ej. k=5 o k=10) para estimar
media y varianza del F1 y reducir dependencia de un solo split.

11.3 Estrategia de validación
Se privilegió un esquema simple y auditable para el informe del curso: métricas
en conjunto de prueba reservado, con escalador ajustado solo en train. El
reporte de clasificación y la matriz de confusión aportan evidencia cualitativa
del comportamiento por clase.


XII. EVALUACIÓN E INTERPRETABILIDAD
--------------------------------------------------------------------------------

12.1 Métricas de evaluación
Accuracy y F1 en test para todos los modelos; para el modelo final, classification_report
y confusion_matrix en el notebook.

12.2 Análisis de resultados
En la ejecución documentada, el árbol seleccionado alcanza accuracy y F1 iguales
a 1.0 en el conjunto de prueba. Desde el punto de vista de rigor científico,
métricas perfectas sugieren revisar posible sobreajuste, fuga sutil de
información o facilidad del split; se recomienda validación cruzada, curvas
PR-ROC y prueba con datos totalmente externos.

12.3 Interpretabilidad del modelo
- Para el árbol final: importancia de variables (feature_importances_) y
  estructura de reglas implícita en el modelo.
- El script src/probar_modelo.py imprime coeficientes si el estimador es lineal,
  o primeras importancias si el estimador las expone, verificando la carga del .pkl.


XIII. SISTEMA Y PIPELINE
--------------------------------------------------------------------------------

13.1 Arquitectura del sistema
Componentes: (1) datos raw, (2) notebook de orquestación y análisis, (3) datos
procesados, (4) modelo serializado, (5) script de verificación. Un sistema de
producción real añadiría API, autenticación, registro de predicciones y monitoreo
de deriva.

13.2 Pipeline del modelo
CSV raw → limpieza/imputación → EDA → get_dummies → drop de objetivo para X →
train_test_split estratificado → fit scaler en train → transform train/test →
entrenamiento de modelos → evaluación en test → elección por F1 → joblib.dump
a models/modelo_final.pkl → opcionalmente escritura de dataset procesado.

XV. MEJORAS Y LIMITACIONES
--------------------------------------------------------------------------------

15.1 Limitaciones del proyecto
- Dataset de laboratorio; generalización a población real no demostrada.
- Validación principal en un solo hold-out; falta CV y conjunto de validación
  temporal si hubiera fecha de originación.
- Posible sobreajuste en modelos con desempeño perfecto en test; requiere
  auditoría adicional.
- SVC con kernel por defecto puede no ser óptimo ni escalable a muy alta
  dimensionalidad sin ajuste fino.

15.2 Propuestas de mejora
- Incorporar StratifiedKFold y búsqueda de hiperparámetros (GridSearchCV).
- Ajuste de umbral de decisión según costo FP/FN del negocio.
- Muestreo o pesos de clase ante desbalance.
- Explicabilidad global/local (p. ej. SHAP) y prueba en datos nuevos.
- Contenerizar o exponer endpoint REST para predicción batch.


XVI. CONCLUSIONES
--------------------------------------------------------------------------------
Se implementó un pipeline completo de riesgo crediticio con preparación
transparente de datos, EDA orientado a negocio y comparación sistemática de
cinco algoritmos. El criterio operacional de selección (F1 en test) llevó a
exportar un Árbol de Decisión en la corrida documentada. El repositorio queda
listo para revisión académica y como base para endurecer validación e integración
en producción. Como aprendizaje central, la métrica debe alinearse con el costo
de errores por clase y con protocolos de validación más robustos que un único split.
